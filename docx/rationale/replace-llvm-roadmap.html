替代 LLVM 路线图（2026-11-19 战略转向版）

并行路线（2026-11-19）：本文是「代替 LLVM 编译器后端」主线。另有一条并行路线—— dialpkg-roadmap.md：把包管理打磨成通用 C 包分发标准（C 源码分发、 语义版本、传递依赖、search）。两路线共享护栏、独立推进，互不耦合。

本文取代 roadmap-gap-analysis.md 与 replace-llvm-multidim-audit.md 作为当前主线。 那两份文档记录的是「性能追赶期」的历史盘点与证据链，保留不删；但其中「性能未达标 故不能代替 LLVM」的裁决已因本转向失效，一切以本文为准。

0. 战略转向：从「性能竞赛」回归「代替能力」

用户 2026-11-19 决策原文精神：

目标不是纯粹超越 LLVM，而是代替 LLVM。只要性能够用就行，没必要再死优化—— 运行时本来就有 ±5% 噪声，再优化用户也感知不到。优化到一个足够的性能就足够了。 因此重新制定路线图。

这条决策纠正了过去若干批次的方向偏差：此前把「几何平均 / 加权总耗时再降几个百分点」 当作主线 KPI，投入了大量精力做闭式特化、指令级调度 POC、GRA 微调、ISA 诊断——其中 大量工作证伪为噪声（0.997x~1.001x）或边际递减。在 ±5% 运行时噪声面前，把这些数字从 0.57x 推到 0.55x，用户无法感知，却消耗了本可用于补齐「代替能力」的预算。

新判据： OPT-ENOUGH。性能达到「够用线」即冻结，不再作为投入方向；资源转向功能、 平台、正确性、工程化这些「用户能直接感知、且 LLVM 缺了就不叫代替」的维度。

1. 性能维度：已达「够用线」，正式冻结

1.1 达标证据（同配置 --fast -O3 公平 A/B，背靠背各 2 次）

几何平均比值（asm/llvm，<1 为快） 0.5743x 0.5718x ≤ 1.05x ✅ 领先约 43%
加权总净耗时比 0.9111x 0.9106x ≤ 1.10x ✅ 反超约 9%
逐项胜/平/负 11 / — / 17 10 / — / 18 — ✅ 多数项领先

1.2 「够用线」的定义与理由

  • 几何平均 ≤ 1.05x：几何平均衡量典型程序的普遍表现；≤1.05x 意味着「不比 LLVM 慢」， 落在 ±5% 噪声内即视为等价。当前 0.57x，裕度极大。
  • 加权总耗时 ≤ 1.10x：总耗时反映重负载总和；≤1.10x 意味着整体不落后。当前 0.91x， 已反超。
  • 两条都满足即判定 性能达标（OPT-ENOUGH）。当前早已满足，且经过 9 轮 targeted 优化（数组 get/set 内联、字符串静态化、尾调用帧复用、GRA span×freq、递归闭式、线性 递推闭式等）验证稳定，非单点侥幸。

1.3 ±5% 噪声的量化认知

历史 POC 已经反复证明边际优化落在噪声内：冗余 mov 消除 0.997x、魔数外提 0.998x、 循环展开 1.001x、逐指令复刻 0.998x、PGO 布局 0.997x。这些数字即使全部达成，也改变 不了用户哪怕一帧的体验。 继续在此投入是负 ROI（机会成本 = 未补齐的代替能力）。

1.4 冻结清单（性能优化方向一律不再投入）

以下方向全部冻结，除非命中第 5 节重启条件：

方向 历史结论 冻结状态

span×freq 高级分配优先级 M8 已落地、含-call 退化已回退 ❄️ 冻结（保留现状）
递归闭式 / 线性递推闭式 M8/M9 已落地 ❄️ 冻结（保留现状）

重要区分：冻结的是「以性能为目标的 Further optimization」，不是回退已落地的优化。 现有全部优化成果作为基线保留，tools/bench_asm_vs_llvm.py 与 golden 门禁继续存在， 但用途从「优化 KPI」降级为「回归护栏」——只在这些指标因其它改动而意外退化时报警。

2. 新重心：代替能力完备（用户可感知的维度）

性能达标后，「能否代替 LLVM」的判据完全落在功能、平台、正确性、工程化上。按此 重新排序，剩余待办如下（这是本路线图真正要推进的内容）。

P0 · 正确性底线（最高优先，属「代替」的硬前提）

  • ~~map 的 string key 本地引用未归还：50 万次 put/remove 循环泄漏约 30MB~~ —— 归因修正 + 已修复（2026-11-19）：隔离实验证明 map 常量 string key 不泄漏；真正 泄漏源是 string 拼接 / 插值的 lowering 未归还自带所有权的临时操作数。C runtime dial_string_concat / dial_string_new / *_to_string 只读不消费操作数，而 "k"+str(i) 的 str(i) 中间值没有 Local 持有、concat 后不 release → 每轮循环泄漏一份（~31B/轮，N=50万 17MB、N=200万 64MB，线性增长）。修复（src/lower.rs）：concat 后 release owned 操作数、 插值逐段追踪 owned 状态并结算，借用引用（变量/字段/下标/get/at）与静态串（immortal）跳过。 门禁：tools/verify_string_arc_no_leak.sh（RSS 斜率断言 + 双后端输出一致）；实测 concat/interp/chain 各 20 万次 RSS 由修复前 ~7MB 降至 ~1.4MB；新增 golden tests/asm_golden/string_concat_arc.dial（借用/owned/嵌套/map get/重复用/真插值/循环混合） 双后端逐字节一致，差分 fuzz 450 零不一致，无 double-free / heap assert。§19 零泄漏底线恢复。
  • 复核其它容器键类型的所有权结算（int key 已验证无泄漏；string key 经归因修正后亦确认无泄漏）。

P1 · 平台覆盖（「唯一后端」必须跨平台可用）

  • ~~AArch64 只验证汇编写法、未实机跑语义~~ —— 已收口（2026-11-19）：安装 qemu-user-static 8.2.2 + aarch64-linux-gnu-gcc 13.3 + aarch64 sysroot，实机跑 golden 后一次抓出 3 个语法校验永远发现不了的根本 bug（全部已修，仅 src/codegen_asm.rs）： ① LR(x30) 未保存——x30 是 caller-saved，bl 覆盖后末尾 ret 跳回最后一次调用的返回 地址→所有含调用的函数死循环（连 main(){return 0} 都 hang，因 codegen 插入的 dial_env_init 也走 bl）；统一给所有 AArch64 函数 prologue str x30、epilogue ldr x30。 ② ICmp fuse 跳过物化——analyze_fusable 把「仅一处 Branch.cond 使用」的 ICmp 标为 不物化，但 fuse 的 cmp+jcc 只实现了 x86，AArch64 分支仍 cbz cond 读未写槽→while 条件随机→死循环；AArch64 禁用 fuse、ICmp 一律物化。③ PtrAdd 发射笔误——写成 add o,b,b（o=b+b、b 不变）而非 add b,b,o，p.offset(1) 指针偏移完全失效（连带 simd lane 提取错位）；修正操作数顺序。实机验证：golden 22 用例（inline_asm 预期 Fail-Fast 降级 skip）x86 LLVM 与 AArch64 asm qemu 实机输出 22/22 逐字节一致，x86 golden 24 用例 零回归、差分 fuzz 450 零不一致、全量 run_tests 全绿。门禁固化为 tools/verify_aarch64_semantics.sh（缺 qemu/交叉 gcc 自动 skip，挂入 run_tests.sh AI 段）。
  • ~~DWARF 在 AArch64 降级~~ —— 已收口（2026-11-19，P1 平台对等）：手写 DWARF v5 生成主体本与目标无关，但被 x86-64 门控硬关。打开后暴露两处目标相关问题并修复（仅 src/codegen_asm.rs）：① .value 伪指令在 aarch64 GNU as 下是 unknown pseudo-op → 改跨平台 .2byte（2 字节同义词，x86 二进制零变化）；② 变量/形参 location 的 DW_OP_breg7(rsp)=0x77 是 x86 专用 → AArch64 用 DW_OP_breg31(sp)=0x8f（DWARF for AArch64：sp=31），偏移仍为相对当前 sp 的 alloca_off（与 x86 rsp 同构、绕开 frame_base）。 三处门控（.file 表 / CU / end_label）统一走 dwarf_enabled 共因函数，杜绝 high_pc 引用 未定义标签。实机验证：AArch64 -g 静态 ELF 含 .debug_info/.debug_line、dwarfdump 7 符号齐全 + 行表含源名 + --verify 无错误、.s 中 breg=0x8f 且无 0x77 残留、qemu gdbstub 实机 break dbg.dial:9 命中 + print counter=42 + bt 显示源码行；无 -g 零 符号。交付门禁 tools/verify_aarch64_dwarf.sh（缺 qemu/交叉 gcc/gdb 自动 skip，挂入 run_tests.sh AJ 段），全量 run_tests（含 R2 x86 DWARF / AI 语义 / AJ DWARF）全绿。
  • ~~AArch64 能力降级项——逐项裁决为「可接受降级」（2026-11-19）~~ —— 已补齐 （2026-11-20，P4.5）。用户随后明确要求「把 AArch64 相关补上」，推翻了此前"可接受降级" 裁决。理由校正：这两项是 A 类「LLVM 有、asm 无」的能力缺口（LLVM 在 AArch64 支持 inline asm 与 PGO），不是性能竞赛——补齐它们不违背"性能冻结"（冻结的是优化投入，不是 功能对等）。同为 1.10.0、零新依赖、LLVM 路径零改动：
  • PGO 放开 AArch64：pgo_active 去掉 target 门控；插桩改 target-aware—— counter_inc 用 adrp + add :lo12: 取 .comm 地址、ldr/add/str 自增（add 不改 NZCV， scratch x9/x10/x11 在驻留开启前无活跃值）；dump 用 stp/ldp 保护 x0-x17 + LR(x30) （AArch64 bl 覆盖 LR，x86 call 压栈不覆盖）。训练二进制 -static 链接 + qemu-aarch64-static 执行（原生 AArch64 直接跑），缺 qemu 当场 Fail-Fast（不静默降级伪装成功）。门禁 tools/verify_aarch64_pgo.sh 六层证据（magic/计数反映真实执行/冷热分段/qemu 输出一致/ 确定性/Fail-Fast）全绿，挂 run_tests.sh AP3 段。
  • 内联汇编放开 AArch64：去掉两处 Fail-Fast 预检；inst_inline_asm/render_asm_template 改 target-aware——操作数池 x86 rdi..r9 → AArch64 x0-x5、i8/i1 零扩展 movzbq → uxtb、 AArch64 寄存器裸名（不加 ATT 的 %）、Intel 方言切换仅 x86 发射。模板按目标汇编语法书写 （与 LLVM 一致）。门禁 tools/verify_aarch64_inline_asm.sh qemu 实机逐值验证 identity/ add7/byte/Intel 方言 + 形态断言（裸名/无方言切换/uxtb）全绿，挂 AP4 段；x86 双后端零回归。 核心运行语义（AI）、源码级调试（AJ）、PGO（AP3）、内联汇编（AP4）现均在 AArch64 实机验证。

P2 · 功能对等（B 类语言特性，按「LLVM 不存在」总纲裁决）—— ✅ 已全部收口（2026-11-19）

以下 LLVM 后端也没有，但按「假设 LLVM 不存在、只有自己」总纲，它们是语言层真实能力 缺口，需独立裁决是否纳入（不再是「LLVM 也没有所以不算差距」）。本轮已逐项给出终态， 消除原「建议纳入 / 需设计 / 默认不进」这类未决措辞与 README 能力表的自相矛盾：

项 终态（2026-11-19 收口） 证据 / 裁决理由
select 语句级超时 ✅ 已落地（v1.10，select(ms){...timeout{...}}，可选块级超时） 提交 1ce1061（双后端一致）；README 能力表已标「已支持」；底层 pthread_cond_timedwait + 绝对 deadline，与 default 并存时 default 优先
map<K,string> 值 / values() 非 int ✅ 已落地（v1.10，V=string / 标量字段结构体 + values() / get_or()） 提交 0d13bbd（values/get_or 放开 string 值并修默认值所有权）、31d4e40（B6b struct 进 map）；README §29.5 已标「已支持」；未命中返回进程级 immortal 静态空串
原子类型 / 无锁结构 ⛔ 宪法永久否决（不再列「待裁决」） 与 §37.1「可变全局状态永不提供」及 CSP 式 channel + move_to 零竞争并发宪法（§27）根本冲突；无锁正确性（ABA / 内存序 / 安全回收）违反 §1「比 C 更严格」与 §19/§20 内存底线；底层同步需求走 §33 FFI 接 C11 atomics / pthread 原语。理由正式入 README §37.2 永久否决表
print(str(i)) owned 临时直传只读消费方泄漏 ✅ 已裁决「两边都缺暂不管」 见下方跨后端内存缺口说明；两后端行为一致、不构成相对差距，修复须双后端同步改所有权契约，不塞进 asm 批次

四项终态：两项已落地、一项宪法否决、一项「两边都缺暂不管」裁决——P2 无未决项，满足 验收判据④「各项有明确裁决（纳入并落地，或宪法否决并记录理由）」。

说明：已落地的两项走的是独立语言版本主题（v1.10 改 codegen.rs/semantic.rs）， 均双后端同步 + 全门禁，与 asm 后端优化解耦；本轮收口只修文档记载，零产品代码改动。

跨后端内存缺口（P0 审计延伸发现，2026-11-19，单列 P2 裁决）：print(str(i)) 这类 「owned 临时直传只读消费方（无变量承接）」两后端都泄漏（30 万次 RSS asm 10.5MB / LLVM 10.8MB）——LLVM emit_print→dial_print_string 只读不消费、print 路径未调 settle_fresh_value，与 asm 同缺。因两后端行为一致、不构成 asm 相对 LLVM 的差距，且真正修复 须双后端同步改所有权契约（print/open/write/== 等所有只读消费方），按「两边都缺暂不管」 裁决不擅改、不塞进 asm 批次。asm 拼接/插值主路径（concat/interp）泄漏已于 P0 修复。 证据链见 unreleased-dev.md。

P3 · 工程化与文档（可信度与可维护性）—— ✅ 已全部收口（2026-11-19）

  • 过时结论清理 ✅：roadmap-gap-analysis.md 第 1 节的「领先 46%」删节线、 replace-llvm-multidim-audit.md 的「当前不能代替」裁决、诊断工具里的旧口径——顶部转向 声明均已在位（历史证据链保留不删，一切以本转向版为准）。本轮另清理 P2 记载与 README 能力表的自相矛盾（见 P2 段收口）。
  • 门禁盲区固化 ✅：B6 struct 进容器此前只修 asm 并纳入 asm 门禁，但差分 fuzz 生成器 只生成局部 PT{} 调方法、从不把 struct 装进容器，存在「两边都能编译才比一致」掩盖 「一边根本编不过」的盲区。本轮扩展 tools/diff_fuzz.py：① prelude 声明带默认值的 struct PT，新增 struct_container_ops 生成 PT[] 字面量 / 下标读 / 下标写 / set / push 与 map<string,PT> 的 put/get/get_or/contains/size/values/remove（严格复用 golden batch3_b6_smoke.dial 已双后端验证的语法）；② fuzz 统计新增「struct 进容器覆盖率 + 一边 编不过」专项计数，生成了该构造却任一端编译失败即判门禁失败（不再当 skip 放过）。 实测：门固定 seed 区间 40000..40149 覆盖 59/150 个程序，150 seed × O0/O2/O3 = 450 次 全 OK、0 编译失败、0 不一致；PT[] 与 map<string,PT> 两条路径单独编译运行均双端逐字节 一致。
  • 可复现性 ✅：所有「达标 / 代替」结论保持命令可复现、数据可重跑、双次确定性； 新增 fuzz 门禁仍用固定 seed 区间，结果确定。

3. 验收判据（什么叫「已代替 LLVM」）

一条清晰、可检验的线，替代过去模糊的「性能是否领先」：

当且仅当：① 性能维持 OPT-ENOUGH（§1 够用线，已满足）；② P0 正确性缺口清零； ③ P1 AArch64 实机语义 golden 通过 + 源码级调试（DWARF gdb 断点/print）可用；④ P2 各项有明确裁决（纳入并落地，或宪法否决并 记录理由）；⑤ P3 过时结论清理 + fuzz 盲区固化完成——即可宣布 asm 后端在能力上代替 LLVM，此后 LLVM 路径可进入冻结/退役流程。

验收状态（2026-11-19 复验）：① 性能 OPT-ENOUGH ✅（回归护栏）；② P0 string ARC 泄漏修复、 零泄漏底线恢复 ✅；③ P1 AArch64 语义 golden 22/22 + DWARF gdb 断点/print 实机通过 ✅； ④ P2 四项全部终态（select 超时 / map string 值已落地、原子类型宪法否决、print(str) 两边都缺暂不管）✅； ⑤ P3 过时结论清理 + struct 进容器 fuzz 盲区固化（450 次 0 失败）✅。五项全绿，能力上已具备 代替 LLVM 的条件。

性能不再是代替的阻断项——这是本转向与旧审计最根本的区别。

4. 护栏（延续，不变）

  1. LLVM 路径零改动：src/codegen.rs、src/ast.rs 相对基线冻结（P2 若纳入须单独申请放宽）。
  2. AArch64 普通程序零变化（性能冻结意味着更少扰动）；版本 1.10.0；零新依赖；docx 确定性；不打 tag。
  3. 每批带 A/B 回归护栏 + 全门禁 + 证据链（即便不以优化为目标，回归不可破）。
  4. 「假设 LLVM 不存在、只有自己」总纲继续有效，统领一切裁决。

5. 性能优化的重启条件（写死，非满足不重启）

冻结 ≠ 永久删除。命中以下任一，才允许重启对应性能方向的诊断：

  1. 出现新 workload（bench 或真实程序）使 OPT-ENOUGH 指标退化到够用线外（几何平均

    1.05x 或总耗时 >1.10x）；

  2. 语言层新增可并行语义 / 显式向量提示，使此前负 ROI 的方向（SIMD/展开）出现正收益；
  3. P0/P1/P2/P3 全部收口后，仍有明确预算且用户主动要求进一步压榨性能。

不满足以上而「只是想再快一点」——一律不重启，资源留给代替能力。

6. 一句话结论

性能已经够用（几何平均 0.57x、总耗时 0.91x，远超 ±5% 噪声阈值），性能优化正式冻结。 主线是「在功能、平台、正确性上让 LLVM 变得不必要」——P0 正确性泄漏修复、P1 AArch64 实机语义 + DWARF、P2 语言特性裁决、P3 文档与 fuzz 盲区收口均已完成，五项验收全绿， 能力上已具备代替 LLVM 的条件。性能只作回归护栏，不再投入；下一步按用户门槛复核后再推进 并行的 P4 包管理路线。
