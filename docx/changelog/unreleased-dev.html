  • 里程碑：整体几何平均首次反超 LLVM（1.0794x→0.9793x）——dial_array_set 独占快路径内联：数组内存类原是最大短板（b15 冒泡 2.676x、b17 矩阵乘 2.091x），受控实验坐实 dial_array_set 调用占冒泡内层约 80% 开销。实现（仅 src/codegen_asm.rs::inst_call，紧邻 get 内联）：仅 x86-64 + ReleaseFast 下，实参装 rdi/rsi/rdx（回退 call 复用），运行时检查 refcount==1 && kind==0（独占 int[]）→ mov v,[a+24+i*8] 直写返回 a，否则回退原 call 保留 COW/ARC；safe/debug 与 AArch64 原样。正确性：COW 共享写 2 万次压测双后端一致、原数组未污染、glibc 堆检查 0 错误；string[] 引用元素走回退正确；golden 23/22、fuzz 450。实测：数组类 1.556x→1.0945x（b15 2.676→1.195、b17 2.091→1.364、b16 反超 0.912），整体几何平均 1.0794x→0.9793x（首次 <1），胜平负 7/5/16→9/7/12。诚实补充：几何平均已反超，但加权总净耗时仍 1.0728x（慢约 7%），两类指标都记录。总裁裁更新：按几何平均统计意义上追平/反超，按总耗时仍未全面代替；剩余 b12 闭式、b08/b05 算术、b22 substring、GRA 全 spill 架构级工程继续推进。护栏：1.10.0/零依赖/AArch64/LLVM/safe-debug 零变化、不打 tag。证据链见 rationale/unreleased-dev.md。

  • 字符串字面量静态化——b20「x=x+"y" 循环拼接」2.275x→1.084x（-52%，近乎追平 LLVM）：延续代替 LLVM 的性能主线，攻审计「C runtime 字符串路径」架构级差距中最高 ROI 的一点。受控实验坐实循环内 dial_string_new("y")（malloc+strlen+memcpy）占该模式约 50% 开销。实现（仅 asm 路径 ir/lower/codegen_asm/pass）：新增 LeaStaticString IR，字面量在 .rodata 发射为静态 immortal DialString（[rc=INT64_MIN][len][data\0]，retain/release no-op），Expr::StringLit 直接取静态句柄、省去运行时构造；字符串不可变 + 内容比较，语义等价；LLVM 后端从 AST 直接生成、零改动。实测全 .s 中 dial_string_new 调用 23→0，字符串类几何平均 ~1.33x→1.083x，整体 1.0891x→1.0794x。修复既有测试 UB：R11 probe 原用 extern strchr 裸 C 指针当 string 句柄（旧版 exit=132 double-free，只看 stdout 漏检），静态化进 .rodata 后更早暴露为 SIGSEGV；改用 channel close+recv 的合法 null 来源重写（各优化级别双后端一致、exit=0），不改编译器语义、不掩盖 bug。验证全绿：golden 23/22 + 差分 fuzz 450 + 工具链 22 + PGO + 全量 run_tests + ARC 压测 + glibc 堆检查。护栏：1.10.0/零依赖/LLVM 路径零改动/不打 tag。证据链见 rationale/unreleased-dev.md。

  • 互递归尾调用帧复用——b12 互递归 4.263x→3.360x：延续代替 LLVM 的性能主线，数据定位 b12 互递归奇偶判定 4.263x 为最突出单点缺口（递归类其他项 0.066x/0.342x 领先）。根因：elide_tail_calls 虽已把 evR/odR 的 call→jmp，但每层互跳仍 subq $120 建帧+movq 存参+addq $120 拆帧，60 层×2 万轮=上百万次冗余栈操作。实现（仅 src/codegen_asm.rs::elide_tail_calls 扩展）：caller/callee 同签名、同帧大小、无 callee-saved 时，尾跳保持 rsp 不变、跳到 callee prologue 内别名标签（跳过 subq、保留参数保存），N 层递归只建/拆一次帧；帧大小不同自动退回普通尾调用。踩坑：初版别名标签误插在参数保存之后，尾跳跳过保存致递归读到旧参数永不终止（b12 跑 6 分钟超时、最小程序 timeout）；修正为插在参数保存之前，新增 tests/asm_golden/mutual_recursion.dial（单/双参数互递归）钉死，ReleaseFast 双后端门禁覆盖。实测 b12 4.263x→3.360x（-21%）、递归类 0.5562x→0.5316x、整体 1.0905x→1.0891x（噪声内）；剩余 3.36x 是递归 vs LLVM 折叠成 n%2 闭式的本质差距，属前端优化不动。验证：golden 23+22、差分 fuzz 450、工具链 22、PGO L1-L4、全量 run_tests 全绿。护栏：1.10.0/零依赖/AArch64/LLVM 路径零变化、不打 tag。证据链见 rationale/unreleased-dev.md。

  • asm 后端自行内联 dial_array_get——攻性能硬阻断，数组内存类 1.60x→1.485x：延续「代替 LLVM」主线，多维度审计裁决功能缺口 B6 已修复后，唯一剩余硬阻断是性能（公平 --fast -O3 A/B 整体慢约 12%、数组内存类慢 60%）。根因坐实：数组下标 a[i] 降级为 C runtime dial_array_get(a,i) 调用，其函数体在 ReleaseFast（DIAL_SAFETY=0，边界检查编译期消除）下等价于一条 load [a+24+i*8]（payload 布局 [kind][len][cap][elems@24]）；手写汇编调预编译 C 函数无法被链接期 LTO 内联，每次读都付 call/ret+ABI 开销——正是 LLVM 靠 --fast LTO 吃掉、asm 长期吃不到的部分。实现（仅 src/codegen_asm.rs::inst_call，+38 行）：x86-64 + ReleaseFast + 签名 [Handle,I64]->I64 时用发射临时 rax/r10 就地发射 shlq/addq/movq 24(...) 内联读，跳过 call；safe/debug 保留原 call（Fail-Fast 边界检查不绕过）、AArch64 保持原 call、IR/lower/LLVM 路径零改动。实测（公平 A/B，校验和锚点保证等价计算）：数组内存类几何平均 1.60x→1.485x、整体 1.1155x→1.0905x（仍慢约 9%）、胜平负 6/6/16→6/7/15；.s 中 dial_array_get 调用 23→0。门禁补盲区：原 golden 用默认 ReleaseSafe 测不到内联路径，在 tools/run_asm_golden.sh 新增 ReleaseFast 双后端对比组（21 用例，LLVM LTO 内联 vs asm 发射内联输出须逐字节一致）。验证全绿：ReleaseFast 双后端 21 + 默认 golden 22 + 450 差分 fuzz + 工具链去 LLVM 化 + 自研 PGO L1-L4 + 全量 run_tests。总裁裁不变（仍慢约 9%，剩余是 GRA 全 spill + C runtime 字符串 + LTO 整体调度架构级工程，量化搁置）；dial_array_set 内联因 COW+所有权+C 布局耦合风险/收益不划算，本轮不动。护栏：1.10.0/零依赖/AArch64/LLVM 路径/safe-debug 行为零变化、不打 tag。证据链见 rationale/replace-llvm-multidim-audit.md。

  • asm 后端补齐 B6「结构体进容器」——消除审计发现的功能硬缺口：多维度审计（rationale/replace-llvm-multidim-audit.md）实测发现此前 README 声称的「B6 双后端一致」失实——run_tests.sh 用默认 LLVM 编译 batch3_b6_smoke.dial，从未验证 asm；实际上 asm 在 coerce_elem_bits 对 struct 直接 Fail-Fast，batch3_b6_smoke 在 asm O0-O3 全部编译失败而 LLVM 正确运行。本批修复：src/lower.rs 的 coerce_elem_bits 支持 struct 装箱（dial_struct_box→payload 指针位模式）、reinterpret_bits 支持非 null 解箱 memcpy、新增 unbox_struct_nullable（无分支 select 方案——无条件 memset 零值模板 + 用经充分验证的 select_values 选源地址 + 单次 memcpy，规避手写跨块 phi 的落地 bug）处理 map get 未命中零值；补齐 put/get_or/remove 的 box 所有权结算（对齐 LLVM sink_elem_after_retain/remove 移交/get_or 默认 box 归还）。验证：batch3_b6_smoke.dial asm O0-O3 全部编译、四级别与 LLVM 输出逐字节一致、5 万次 put/get/remove/get_or 在 heap assert 下无 double-free/UAF、int-key 50 万次 put/remove 无内存泄漏（asm 1440KB≈LLVM 1664KB）；新增 tests/asm_golden/batch3_b6_smoke.dial（golden 22 个全绿）+ V 组 O0-O3 断言。发现一个独立既有问题（不在本轮范围）：map<string,*> 的 string key 本地引用未归还，50 万次循环泄漏约 30MB（map<string,int> 同样复现，与 struct 无关），记入独立待办。护栏：codegen.rs/ast.rs/C 运行时/1.10.0 零改动、零新依赖、AArch64 零变化、baseline .s 零回归、不打 tag。证据链见 rationale/replace-llvm-multidim-audit.md。

  • 收回路线图第 4 项「PGO / LTO / bitcode 自建」——自研 PGO 闭环落地，唯一后端收回路线图四项全部收口（R4）：让 --pgo 在 asm 后端可用且零 bitcode / 零 LLVM 工具依赖。诊断先行（tools/diag_pgo.py）：核实 LTO 源码级已天然单编译单元、包名级是 C .a 非 IR（无 IR 层工作量），bitcode 只是喂 clang 的手段非能力；实测 asm 默认块布局 55 回边循环头 100% 对齐、热路径 fallthrough、冷块甩末尾——通用块重排负 ROI（不硬做）。真正缺口是 --pgo 在 asm 下被 exit(1) 拒绝。实现：① src/pgo.rs 自研 .dialprof 纯文本格式（DIALPGO1 + 计数行，load 严格 Fail-Fast + merge，7 单测）；② runtime/dial_rt_pgo.c 的 dial_pgo_dump 读 DIAL_PGO_FILE 写回 profile（未设置则 no-op，自动编入 libdial_std.a）；③ codegen_asm.rs 的 PgoPlan 三态——instrument 发 .comm 计数器 + pushfq/incq/popfq 插桩 + main 返回前保护 9 个易失寄存器后 dump（避免破坏返回值，已实证 lg(Value::Reg) 驻留取源风险），optimize 做热函数判定（入口+循环计数、相对阈值 max×10%、main 强制、全零回退）与 .text.hot/.text.unlikely 分段 + 冷函数省循环对齐；④ main.rs 两段式编排（插桩编译→训练运行→读回→优化重编），asm PGO 独立于 --fast，删除原拒绝。零回归铁证：24 源码 -O3 .s 与基线逐字节一致、baseline 路径 profile=None 全短路、AArch64/-g 不进 PGO；端到端输出与 baseline 一致、profile 反映真实热路径且确定、冷热分段归属正确。性能如实记录：A/B pgo/baseline≈0.997（中性偏微正、噪声内）——与诊断一致：默认布局已近最优，PGO 核心价值是功能完整性非性能飞跃，不硬声称加速。门禁 tools/verify_asm_pgo.sh（run_tests.sh AR 组）四层证据全绿。护栏：零新依赖、codegen.rs/ast.rs/1.10.0 零改动、AArch64 零变化、不打 tag。证据链见 rationale/roadmap-gap-analysis.md。

Fixed

  • http.dialpkg：chunked 长度行不再静默损坏（§20 Fail-Fast）。dial_http.c 的 dh_read_chunked 用 strtoll(line, &endp, 16) 解析块长度却不检查 endp != line： 服务器返回 xyz 时 strtoll 返回 0 且 endp == line，畸形响应被当成「结束块」， 响应体凭空少一截却报 200。现补四道检查：endp == line（一个十六进制数字都没 解析到）、errno == ERANGE（溢出）、负数、以及长度数字后除 ;chunk-ext / 行尾空白 以外的脏尾随字符；任一命中即 DIAL_HTTP_ERR_PROTOCOL 并把坏行写进错误槽，合法 1a;ext=1 扩展照常放行。errno.h 提到文件顶部无条件包含，Windows 分支同样生效。
  • http.dialpkg：Termux 目标平台能加载系统根证书库。dial_tls.c 的 load_linux_ca 原本只读 /etc/ssl/certs 与 /etc/ssl/cert.pem，而 Termux 的证书在 $PREFIX/etc/tls/cert.pem——文档把 Termux 列为目标平台，https 却直接报 「无法加载系统根证书库」。现按 getenv("PREFIX") 的实际长度动态拼该路径 （绝不静默截断），加载成功即计入受信链；失败时的中文提示同步列出 Termux 路径。 自定义 CA 优先级与 fail-closed 证书校验一点未动。
  • http.dialpkg：额外请求头不再被 512 字节静默截断。dial_http2.c 的 h2_submit 原用 char buf[512] 且 llen 超限就截到 511 字节：很长的 Authorization / Cookie 会被悄悄砍掉，请求照样发出却鉴权失败。现按行长 malloc 整行 （dh_hlist_add 本就拷贝 name/value，用完即释放），分配或入表失败按 Fail-Fast 整条请求失败、不发半截头。HTTP/1.1 侧 dh_request 本就走动态 dh_buf，无此问题。
  • http.dialpkg：HTTP/2 额外头名统一小写化（去掉截断后暴露的协议合规坑）。 RFC 7540 §8.1.2 要求头名必须小写，用户按 HTTP/1.1 习惯写的 Authorization: <超长 token> 会被对端以 ProtocolError 拒绝。现 h2_submit 只把 extra_headers 的头名转小写，H1 侧大小写不敏感、保持原样；.diali 对外签名与 abi = 6 均不变（仅注释补充，pack 时重算 SHA256、install 同 ABI 覆盖）。
