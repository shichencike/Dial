逐条详情

CVE-2026-DIAL-001 中

发现版本 v0.98.0 · 存活 1 个发布版本 · 关联缺陷 #103 · 修复版本 v0.98.1

漏洞描述

解析器的 parse_primary 漏掉了 LParen 分支，导致任何以左括号开头的分组表达式 ( … ) 都会报 期望表达式，但遇到 LParen。表达式语法缺少最基础的优先级分组能力。

影响

所有需要使用括号显式控制求值顺序的算术/逻辑表达式无法编译；用户被迫改写成无括号形式，降低可读性且易引入优先级错误。

概念验证（PoC）

fn main(): int {
    let i: int = 10;
    print(i - (i/3)*3);   // 期望输出 1
    return 0;
}

修复方式

在 parse_primary 中增加 TokenKind::LParen 分支：消费左括号后递归 parse_expr()， 再 expect(RParen) 匹配右括号，将内层表达式原样返回。修复后上述 PoC 正确输出 1。

CVE-2026-DIAL-002 高

发现版本 v0.98.0 · 存活 1 个发布版本 · 关联缺陷 #104 · 修复版本 v0.98.1

漏洞描述

dialc run <文件> 在计算输出路径时，若传入裸文件名（无目录部分）， Path::parent() 返回空路径。空路径被直接拼接进链接命令行，最终解析为 /bin/<name>——也就是说，当你想运行当前目录下的 test.dial 时， 编译器静默地尝试执行根目录的 /bin/test，并以 “No such file or directory” 报错或行为错位。

影响

用户在项目子目录中以相对路径运行源文件时，编译器并不能定位到正确的文件，构建/运行结果错误且提示误导性强， 是典型的高影响可用性与正确性缺陷。

概念验证（PoC）

# 在任意子目录内，用相对路径运行同名文件
mkdir -p sandbox && cd sandbox
echo 'fn main(): int { print("run relative path works"); return 0; }' > poc_002_run.dial
dialc run poc_002_run.dial     # 修复后输出: run relative path works

修复方式

在 output_paths 中，对 parent() 返回空（或空 os_str）的情况统一归一化为 "."，确保链接器与运行时都从当前工作目录解析源/输出文件。修复后相对路径可被正确定位。

CVE-2026-DIAL-003 严重

发现版本 v0.98.0 · 存活 1 个发布版本 · 关联缺陷 #105 · 修复版本 v0.98.1

漏洞描述

dial_rc_clone 在引用计数为 1 时直接返回同一个指针却未执行 retain （refcount += 1）。于是“克隆”出的新变量与原变量共享同一块内存——这既是数据污染（改一处影响另一处）， 也是数据竞争（多线程下两个 +0 引用彼此释放）。

在定位该问题的过程中，还暴露出更深层的数组 use-after-free：dial_array_set / grow 在“返回同一指针”的 COW 路径内部自行调用 dial_rc_release，与赋值语句“释放旧值”的约定冲突， 使自赋值 a = a.set(...) 出现“释放后被复用”的悬垂。

影响

任何把容器（数组/字符串/哈希表）赋值给第二个变量再独立修改的场景，都可能产生不可复现的内存破坏、 越界、崩溃或跨线程数据错乱。严重程度最高。

概念验证（PoC）

fn main(): int {
    let a: int[] = [1, 2, 3];
    let b: int[] = a.clone();   // 克隆
    b.set(0, 99);               // 只改副本
    print(a.get(0));            // 期望 1（原件不受影响）
    print(b.get(0));            // 期望 99（副本独立）
    return 0;
}

修复方式

(1) dial_rc_clone 在 refcount==1 的分支改为 refcount += 1 再返回， 使克隆对象获得独立所有权。(2) dial_array_set 与 grow 在“返回同一指针”时遵循 所有权转移约定：返回 +1 的指针，由赋值语句统一释放旧值——彻底消除自赋值的悬垂。 修复后 PoC 稳定输出 1 与 99，重复运行无越界/崩溃。

CVE-2026-DIAL-004 高

发现版本 v0.98.0 · 存活 1 个发布版本 · 关联缺陷 #106 · 修复版本 v0.98.1

漏洞描述

异常机制依赖 setjmp/longjmp 实现零成本 try/catch，但跳转目标 （exbuf）原本由编译期的全局/栈变量管理，无法跨栈帧 unwind。 子函数（如 open()）抛出的异常无法被调用方的 try/catch 捕获， 直接在子函数内部 panic，破坏了“业务失败与系统崩溃分离”的异常设计契约。

影响

跨函数错误处理失效——深层 IO/解析错误无法在入口处统一捕获，迫使程序在内部崩溃，严重影响健壮性与可恢复性。

概念验证（PoC）

fn open_file(): int {
    open("this-file-does-not-exist.txt", "r");  // 抛 Error
    return 0;
}
fn main(): int {
    try {
        open_file();
    } catch e {
        print("caught the error in main!");     // 期望被调用方捕获
    }
    print("after try");                          // 期望继续执行
    return 0;
}

修复方式

引入基于 __thread 线程局部存储的运行时异常栈 （dial_exc_push / dial_exc_pop / dial_exc_top，容量 256）。 try 在进入时 dial_exc_push(buf) 后 setjmp； emit_throw 从栈顶取出当前捕获栈帧的 exbuf 执行 longjmp，从而实现跨函数 unwind。 修复后 PoC 输出 caught the error in main! 与 after try。

CVE-2026-DIAL-005 中

发现版本 v0.98.0 · 存活 1 个发布版本 · 关联缺陷 #107 · 修复版本 v0.98.1

漏洞描述

语言缺失取模运算符 %：词法分析、语法分析与语义/代码生成三层都未实现。 整数与浮点的取模只能靠用户手写循环或调用 C，且缺少除零保护。

影响

周期性计算（哈希、循环队列、时间换算）只能绕路实现；没有内置取模也让算法表达不自然。

概念验证（PoC）

fn main(): int {
    print(10 % 3);      // 期望 1
    print(10.5 % 3.0);  // 期望 1.5
    return 0;
}

修复方式

词法层新增 TokenKind::Mod 识别 %；parse_factor 识别为二元运算符 BinOp::Mod；语义层对 int/float 校验类型；代码生成层对整数发射有符号 srem、 对浮点发射 frem，并通过 emit_div_zero_check 做除零保护。 修复后 PoC 输出 1 与 1.5。

CVE-2026-DIAL-006 中

发现版本 v0.98.0 · 存活 1 个发布版本 · 关联缺陷 #108 · 修复版本 v0.98.1

漏洞描述

缺失基本类型 → 字符串的转换能力：没有 int_to_string / float_to_string， 也没有统一的 str() 函数；同时字符串拼接只支持 concat() 方法、 不支持更直观的 + 运算符。

影响

数值无法方便地拼进日志/输出，迫使开发者用不自然的 API 组合；语法层面与直觉不一致。

概念验证（PoC）

fn main(): int {
    print("Result: " + str(42));   // 期望 "Result: 42"
    print("Hello" + " World");     // 期望 "Hello World"
    return 0;
}

修复方式

stdlib 新增 dial_int_to_string（snprintf("%lld")）与 dial_float_to_string（snprintf("%.6g")）； 代码生成层让 str() 对 int/float 调用对应 C 函数、对 String 直通； String + String 复用已有的 dial_string_concat。 修复后 PoC 正确输出两行拼接结果。

CVE-2026-DIAL-007 高

发现版本 v0.98.0 · 存活 1 个发布版本 · 关联缺陷 #110 · 修复版本 v0.98.1

漏洞描述

dial_channel_release 释放通道时，环形缓冲区里尚未被消费的元素没有逐一析构。 每个元素本身都是 ARC 指针（如 string / array / 嵌套 channel），只释放通道外壳而不释放这些元素， 造成内存泄漏，并让底层对象引用计数永远无法归零。

影响

长时间运行、频繁创建通道且存在未消费元素的程序会持续泄漏内存，是服务类/并发程序的高危缺陷。

概念验证（PoC）

// 往通道塞 3 个字符串后关闭并释放，但从不 recv
let ch: channel<string> = channel(4);
move_to("one", ch);
move_to("two", ch);
move_to("three", ch);
close(ch);
// release 时 3 个残留 string 必须一并析构，否则泄漏

修复方式

DialChannelImpl 增加 void (*elem_release)(void *) 函数指针； dial_channel_new(4, elem_release) 默认指向 dial_rc_release。 dial_channel_release 在 free 前遍历环形缓冲，对每个元素调用 elem_release。代码生成层的 channel 内建会按元素类型注入正确的 release 函数 （嵌套 channel 用 dial_channel_release，否则 dial_rc_release）。 暴力检测器以“计数版 elem_release”确定性验证：修复后 3/3 残留元素均被释放。

CVE-2026-DIAL-008 低

发现版本 v0.98.0 · 存活 1 个发布版本 · 关联缺陷 #109 · 修复版本 v0.98.1

漏洞描述

三项工程化缺陷：(1) 编译器未尊重 DIAL_C_COMPILER 环境变量，用户无法指定替代的 C 编译器； (2) 打包脚本生成的 BUILD_INFO.txt 文案自相矛盾（同时出现本地与 CI 构建措辞）； (3) 安装脚本对 stdlib / VSIX 的下载不支持断点续传与镜像地址，弱网环境易失败。

影响

可移植性与发布可靠性问题：受限环境无法指定编译器、构建信息误导、安装在大文件下载中断时无法续传。

概念验证（PoC）

# 把 C 编译器指向一个必定失败的程序，若被尊重则应编译失败
DIAL_C_COMPILER=/bin/false dialc run hello.dial
# 期望：dialc 报告 "C 编译器: /bin/false" 并失败（证明变量被读取）

修复方式

(1) cc_command() 在平台候选列表之前优先读取 DIAL_C_COMPILER （按空白分词，首 token 为程序、其余为参数）。(2) 打包脚本以 BUILD_BY 变量区分 “由 GitHub Actions 构建” / “本地构建”，并修正矛盾的回退文案。(3) install-dial.sh 支持 STDLIB_URL 覆盖下载地址，并对 stdlib / VSIX 下载加 -C -（断点续传）。 暴力检测器以“注入记录调用的包装脚本”验证变量被尊重。

检测与回归

所有已登记的 CVE 都由 tools/cve_check.py 暴力检测器持续回归。该工具为每个漏洞构造触发用例（PoC）， 用 dialc 编译/运行，并默认重复 25 次以暴露非确定性缺陷（数据竞争、悬垂、死锁等只在特定调度下显形的内存安全问题）。 任一 CVE 仍可被触发，进程即返回非 0 退出码，CI 据此阻断发布。

# 运行全部 8 个 CVE 的暴力检测（每个重复 25 次）
python3 tools/cve_check.py --repeat 25

# 指定编译器路径 / 静默模式
python3 tools/cve_check.py --dialc ./target/release/dialc --quiet
最新一次本地回归：8 / 8 个 CVE 确认修复，无残留可利用漏洞。该命令已在 CI 工作流 中接入，作为发布前的强制门禁。
