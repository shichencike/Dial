[v0.9] — 2026-10-30

本版做的是并发底座的安全加固：判空、多消费者安全、超时接收 （见 README §27.8）。

最重要的不是新语法，而是修掉了一个真实存在的死锁。 v0.8/v0.81 的通道通知用的是 pthread_cond_signal（只唤醒一个等待者）。 单消费者看不出问题；多消费者下，「队列非空」是众多消费者共享的状态—— 唤醒一个之后若队列仍非空，其余消费者会带着已经失效的等待条件继续睡死。 对照实验（8 消费者 / 100 万元素 / 队列深 64）：signal 版本 25 秒后超时挂死， broadcast 版本 4.25 秒跑完，总数恰好 100 万、零重复、零丢失。

Added（新增）

  • 内建 is_null(x)：句柄判空。准入名单 string / int[] / map / error / channel<T> / thread / file；int / float / bool 是值类型、永远非空， 编译期直接拒绝（而不是让它变成恒为 false 的死代码）。 IR 层只是一次指针比较（ptrtoint + icmp eq 0，优化器折叠回 icmp eq ptr %p, null）， 零函数调用、零引用计数操作。
  • 内建 recv_timeout(ch, ms)：带超时的接收。超时或已关闭且已空时返回空指针 （用 is_null 判别），绝不无限期阻塞。 所有权规则与 recv 完全一致。底层就是 pthread_cond_timedwait + 一个绝对时刻， 没有引入任何状态机。
  • 测试组 F：绕开编译器直压 stdlib/dial_channel.c 的并发压测 （tests/stress/channel_mt.c）：8 个消费者抢同一个通道、100 万元素、队列深 64。 用「位图 + 原子 fetch_or」逐个记录领取情况，重复领取即判失败；总数必须守恒。

Fixed（修复）

  • 多消费者丢唤醒（死锁）：通道的所有状态变化通知由 pthread_cond_signal 改为 pthread_cond_broadcast。单消费者下无差别，多消费者下前者会让某个消费者 永久阻塞。正确性优先于惊群开销。
  • 超时不会吞掉元素：pthread_cond_timedwait 返回 ETIMEDOUT 后回到 while 条件 重新判定，若此刻队列非空则正常取走——「元素恰好在超时这一刻到达」也能被拿到。
  • 超时基准钟从 CLOCK_REALTIME 切回 CLOCK_MONOTONIC：底层超时取用的绝对时刻 原先取自 CLOCK_REALTIME，会被 NTP 校时跳变干扰（校时回拨可能让等待被提前唤醒、 前拨则拖长等待）。现已切回单调钟 CLOCK_MONOTONIC，借助 Linux vDSO 直接在用户态读取、 无需系统调用，时间读取更快，且彻底不受 NTP 校时影响；因彻底放弃 macOS， 无需为 pthread_condattr_setclock 的兼容性做任何妥协。

Added（测试与示例）

  • examples/is_null_demo.dial：EOF / 超时 / 真实值三种情形下 is_null 的判定。
  • examples/recv_timeout.dial：超时返回空值；超时与到达同时发生时以「有元素」为准。
  • examples/channel_multiconsumer.dial：两个消费者抢同一个通道。 每个消费者把收到的元素转发到自己的报告通道，主线程分别取数后相加—— 各消费者分到多少不确定，但总数恒为 100（每个元素只被弹出一次）。 注意多消费者必须用 recv + is_null 判结束，不能用 try_recv： 后者在「队列暂时空」时也返回空指针，那不是 EOF，会漏收元素。
  • 负向用例新增 8 个（is_null 作用于标量 / 参数个数 / recv_timeout 的四种错用 / 两个新名字撞保留名）。

Changed（文档）

  • README §27.8 新增「判空、多消费者安全与超时」，§27.9 边界表同步； §18 测试章节补 F 组与新示例清单；§17.2 未实现清单同步。
