> **并行路线（2026-11-19）**：本文是「代替 LLVM 编译器后端」主线。另有一条并行路线——
> [`dialpkg-roadmap.md`](dialpkg-roadmap.md)：把包管理打磨成通用 C 包分发标准（C 源码分发、
> 语义版本、传递依赖、search）。两路线共享护栏、独立推进，互不耦合。

> 故不能代替 LLVM」的裁决已因本转向失效，一切以本文为准。**

## 0. 战略转向：从「性能竞赛」回归「代替能力」

用户 2026-11-19 决策原文精神：

> 目标不是**纯粹超越** LLVM，而是**代替** LLVM。只要性能够用就行，没必要再死优化——
> 运行时本来就有 **±5% 噪声**，再优化用户也感知不到。优化到一个足够的性能就足够了。
> 因此重新制定路线图。

这条决策纠正了过去若干批次的方向偏差：此前把「几何平均 / 加权总耗时再降几个百分点」
当作主线 KPI，投入了大量精力做闭式特化、指令级调度 POC、GRA 微调、ISA 诊断——其中
大量工作证伪为噪声（0.997x~1.001x）或边际递减。在 ±5% 运行时噪声面前，把这些数字从
0.57x 推到 0.55x，**用户无法感知**，却消耗了本可用于补齐「代替能力」的预算。

**新判据**： OPT-ENOUGH。性能达到「够用线」即冻结，不再作为投入方向；资源转向功能、
平台、正确性、工程化这些「用户能直接感知、且 LLVM 缺了就不叫代替」的维度。

## 1. 性能维度：已达「够用线」，正式冻结

### 1.1 达标证据（同配置 `--fast -O3` 公平 A/B，背靠背各 2 次）

| 指标 | 第 1 次 | 第 2 次 | 够用线 | 判定 |
|---|---|---|---|---|
| 几何平均比值（asm/llvm，<1 为快） | **0.5743x** | **0.5718x** | ≤ 1.05x | ✅ 领先约 43% |
| 加权总净耗时比 | **0.9111x** | **0.9106x** | ≤ 1.10x | ✅ 反超约 9% |
| 逐项胜/平/负 | 11 / — / 17 | 10 / — / 18 | — | ✅ 多数项领先 |

> 数据文件：`/tmp/loop_linrec_full.json`、`/tmp/loop_linrec_full2.json`（可复跑）
> 复现：`python3 tools/bench_asm_vs_llvm.py --backend-flags "--fast -O3"`

### 1.2 「够用线」的定义与理由

- **几何平均 ≤ 1.05x**：几何平均衡量典型程序的普遍表现；≤1.05x 意味着「不比 LLVM 慢」，
  落在 ±5% 噪声内即视为等价。当前 0.57x，裕度极大。
- **加权总耗时 ≤ 1.10x**：总耗时反映重负载总和；≤1.10x 意味着整体不落后。当前 0.91x，
  已反超。
- 两条都满足即判定 **性能达标（OPT-ENOUGH）**。当前**早已满足**，且经过 9 轮 targeted
  优化（数组 get/set 内联、字符串静态化、尾调用帧复用、GRA span×freq、递归闭式、线性
  递推闭式等）验证稳定，非单点侥幸。

### 1.3 ±5% 噪声的量化认知

历史 POC 已经反复证明边际优化落在噪声内：冗余 mov 消除 0.997x、魔数外提 0.998x、
循环展开 1.001x、逐指令复刻 0.998x、PGO 布局 0.997x。**这些数字即使全部达成，也改变
不了用户哪怕一帧的体验。** 继续在此投入是负 ROI（机会成本 = 未补齐的代替能力）。

### 1.4 冻结清单（性能优化方向一律不再投入）

以下方向**全部冻结**，除非命中第 5 节重启条件：

| 方向 | 历史结论 | 冻结状态 |
|---|---|---|
| caller-saved GRA / 跨函数 GRA | e3at ROI 否决 | ❄️ 冻结 |
| span×freq 高级分配优先级 | M8 已落地、含-call 退化已回退 | ❄️ 冻结（保留现状） |
| 递归闭式 / 线性递推闭式 | M8/M9 已落地 | ❄️ 冻结（保留现状） |
| 循环指令级调度 / 展开 | 五个 POC 证伪 | ❄️ 冻结 |
| ISA：标量/SIMD 打包/FMA/加密 | 诊断无 workload、量化搁置 | ❄️ 冻结 |
| 字符串 / 数组 C runtime 微优化 | 已接近追平、剩余架构级 | ❄️ 冻结 |
| PGO 布局 / 块重排 | 中性偏噪声、负 ROI | ❄️ 冻结（保留功能完整性） |

**重要区分**：冻结的是「以性能为目标的 Further optimization」，**不是**回退已落地的优化。
现有全部优化成果作为基线保留，`tools/bench_asm_vs_llvm.py` 与 golden 门禁继续存在，
但用途从「优化 KPI」降级为「回归护栏」——只在这些指标因其它改动而意外退化时报警。

## 2. 新重心：代替能力完备（用户可感知的维度）

性能达标后，「能否代替 LLVM」的判据完全落在**功能、平台、正确性、工程化**上。按此
重新排序，剩余待办如下（这是本路线图真正要推进的内容）。

### P0 · 正确性底线（最高优先，属「代替」的硬前提）

- ~~**map<string,\*> 的 string key 本地引用未归还**：50 万次 put/remove 循环泄漏约 30MB~~
  —— **归因修正 + 已修复（2026-11-19）**：隔离实验证明 map 常量 string key **不泄漏**；真正
  泄漏源是 **string 拼接 / 插值的 lowering 未归还自带所有权的临时操作数**。C runtime
  `dial_string_concat` / `dial_string_new` / `*_to_string` 只读不消费操作数，而 `"k"+str(i)` 的
  `str(i)` 中间值没有 Local 持有、concat 后不 release → 每轮循环泄漏一份（~31B/轮，N=50万
  17MB、N=200万 64MB，线性增长）。修复（`src/lower.rs`）：concat 后 release owned 操作数、
  插值逐段追踪 owned 状态并结算，借用引用（变量/字段/下标/get/at）与静态串（immortal）跳过。
  **门禁**：`tools/verify_string_arc_no_leak.sh`（RSS 斜率断言 + 双后端输出一致）；实测
  concat/interp/chain 各 20 万次 RSS 由修复前 ~7MB 降至 ~1.4MB；新增 golden
  `tests/asm_golden/string_concat_arc.dial`（借用/owned/嵌套/map get/重复用/真插值/循环混合）
  双后端逐字节一致，差分 fuzz 450 零不一致，无 double-free / heap assert。§19 零泄漏底线恢复。
- 复核其它容器键类型的所有权结算（int key 已验证无泄漏；string key 经归因修正后亦确认无泄漏）。

### P1 · 平台覆盖（「唯一后端」必须跨平台可用）

- ~~**AArch64 只验证汇编写法、未实机跑语义**~~ —— **已收口（2026-11-19）**：安装
  `qemu-user-static` 8.2.2 + `aarch64-linux-gnu-gcc` 13.3 + aarch64 sysroot，实机跑 golden
  后一次抓出 **3 个语法校验永远发现不了的根本 bug**（全部已修，仅 `src/codegen_asm.rs`）：
  ① **LR(x30) 未保存**——x30 是 caller-saved，`bl` 覆盖后末尾 `ret` 跳回最后一次调用的返回
  地址→**所有含调用的函数死循环**（连 `main(){return 0}` 都 hang，因 codegen 插入的
  `dial_env_init` 也走 bl）；统一给所有 AArch64 函数 prologue `str x30`、epilogue `ldr x30`。
  ② **ICmp fuse 跳过物化**——`analyze_fusable` 把「仅一处 Branch.cond 使用」的 ICmp 标为
  不物化，但 fuse 的 `cmp+jcc` 只实现了 x86，AArch64 分支仍 `cbz cond` 读未写槽→**while
  条件随机→死循环**；AArch64 禁用 fuse、ICmp 一律物化。③ **PtrAdd 发射笔误**——写成
  `add o,b,b`（o=b+b、b 不变）而非 `add b,b,o`，`p.offset(1)` 指针偏移完全失效（连带 simd
  lane 提取错位）；修正操作数顺序。**实机验证**：golden 22 用例（inline_asm 预期 Fail-Fast
  降级 skip）x86 LLVM 与 AArch64 asm qemu 实机输出 **22/22 逐字节一致**，x86 golden 24 用例
  零回归、差分 fuzz 450 零不一致、全量 run_tests 全绿。门禁固化为
  `tools/verify_aarch64_semantics.sh`（缺 qemu/交叉 gcc 自动 skip，挂入 run_tests.sh AI 段）。
- ~~**DWARF 在 AArch64 降级**~~ —— **已收口（2026-11-19，P1 平台对等）**：手写 DWARF
  v5 生成主体本与目标无关，但被 x86-64 门控硬关。打开后暴露两处目标相关问题并修复（仅
  `src/codegen_asm.rs`）：① **`.value` 伪指令**在 aarch64 GNU as 下是 unknown pseudo-op →
  改跨平台 `.2byte`（2 字节同义词，x86 二进制零变化）；② **变量/形参 location 的
  `DW_OP_breg7(rsp)=0x77`** 是 x86 专用 → AArch64 用 `DW_OP_breg31(sp)=0x8f`（DWARF for
  AArch64：sp=31），偏移仍为相对当前 sp 的 alloca_off（与 x86 rsp 同构、绕开 frame_base）。
  三处门控（.file 表 / CU / end_label）统一走 `dwarf_enabled` 共因函数，杜绝 high_pc 引用
  未定义标签。**实机验证**：AArch64 `-g` 静态 ELF 含 .debug_info/.debug_line、dwarfdump
  7 符号齐全 + 行表含源名 + `--verify` 无错误、.s 中 breg=0x8f 且无 0x77 残留、qemu
  gdbstub 实机 `break dbg.dial:9` 命中 + `print counter=42` + bt 显示源码行；无 `-g` 零
  符号。交付门禁 `tools/verify_aarch64_dwarf.sh`（缺 qemu/交叉 gcc/gdb 自动 skip，挂入
  run_tests.sh AJ 段），全量 run_tests（含 R2 x86 DWARF / AI 语义 / AJ DWARF）全绿。
- **AArch64 能力降级项——逐项裁决完毕（2026-11-19）**：
  - **内联汇编 Fail-Fast**：按设计拒绝（仅支持 x86-64 方言），**可接受降级**——非 bug，
    AArch64 无对应内联汇编语义，强造反而破坏 Fail-Fast 哲学；不纳入本批次。
  - **PGO**（`pgo_effective=false`）：**可接受降级**——战略转向后性能已冻结为回归护栏，
    AArch64 无法在本机跑训练样本（`pgo_active` 本就仅 x86），补齐 ROI 为零；保留功能完整性
    即可，不纳入本批次。
  两者均零代码改动，仅在路线图标注裁决理由；核心运行语义 + 源码级调试已在 AArch64 实机验证。

### P2 · 功能对等（B 类语言特性，按「LLVM 不存在」总纲裁决）

以下 LLVM 后端也没有，但按「假设 LLVM 不存在、只有自己」总纲，它们是**语言层真实能力
缺口**，需独立裁决是否纳入（不再是「LLVM 也没有所以不算差距」）：

| 项 | 现状 | 裁决方向 |
|---|---|---|
| `select` 语句级超时 | 底层 `recv_timeout` 已具备，缺多通道语法糖 | 低工作量，建议纳入 |
| `map<K,string>` 值 / `values()` 非 int | semantic.rs 语义层统一拒绝 | 中工作量，需设计 |
| 原子类型 / 无锁结构 | 触及内存模型与并发宪法 | 需宪法裁决，默认不进 |

> 注意：这些要改冻结的 `codegen.rs`/`semantic.rs`，属独立语言版本主题，不塞进 asm 后端批次。
> 若裁决「纳入」，须走双后端同步 + 全门禁，与后端优化解耦。
>
> **跨后端内存缺口（P0 审计延伸发现，2026-11-19，单列 P2 裁决）**：`print(str(i))` 这类
> 「owned 临时直传只读消费方（无变量承接）」两后端都泄漏（30 万次 RSS asm 10.5MB / LLVM
> 10.8MB）——LLVM `emit_print`→`dial_print_string` 只读不消费、print 路径未调
> `settle_fresh_value`，与 asm 同缺。因两后端行为一致、不构成 asm 相对 LLVM 的差距，且真正修复
> 须双后端同步改所有权契约（print/open/write/== 等所有只读消费方），按「两边都缺暂不管」
> 裁决不擅改、不塞进 asm 批次。asm 拼接/插值主路径（concat/interp）泄漏已于 P0 修复。
> 证据链见 [unreleased-dev.md](unreleased-dev.md)。

### P3 · 工程化与文档（可信度与可维护性）

- **过时结论清理**：`roadmap-gap-analysis.md` 第 1 节的「领先 46%」删节线、`replace-llvm-
  multidim-audit.md` 的「当前不能代替」裁决、诊断工具里的旧口径——统一指向本转向版。
  （本轮已加顶部声明，后续逐条收口。）
- **门禁盲区固化**：B6 struct 进容器虽已修复并纳入 asm 门禁，但差分 fuzz 生成器未覆盖
  该构造——扩展 fuzz 语料，避免「两边都能编译才比一致」的盲区掩盖「一边根本编不过」。
- **可复现性**:所有「达标 / 代替」结论保持命令可复现、数据可重跑、双次确定性。

## 3. 验收判据（什么叫「已代替 LLVM」）

一条清晰、可检验的线，替代过去模糊的「性能是否领先」：

> **当且仅当**：① 性能维持 OPT-ENOUGH（§1 够用线，已满足）；② P0 正确性缺口清零；
> ③ P1 AArch64 实机语义 golden 通过 + 源码级调试（DWARF gdb 断点/print）可用；④ P2 各项有明确裁决（纳入并落地，或宪法否决并
> 记录理由）；⑤ P3 过时结论清理完成——即可宣布 **asm 后端在能力上代替 LLVM**，此后
> LLVM 路径可进入冻结/退役流程。

性能**不再是**代替的阻断项——这是本转向与旧审计最根本的区别。

## 4. 护栏（延续，不变）

1. LLVM 路径零改动：`src/codegen.rs`、`src/ast.rs` 相对基线冻结（P2 若纳入须单独申请放宽）。
2. AArch64 普通程序零变化（性能冻结意味着更少扰动）；版本 1.10.0；零新依赖；docx 确定性；不打 tag。
3. 每批带 A/B 回归护栏 + 全门禁 + 证据链（即便不以优化为目标，回归不可破）。
4. 「假设 LLVM 不存在、只有自己」总纲继续有效，统领一切裁决。

## 5. 性能优化的重启条件（写死，非满足不重启）

冻结 ≠ 永久删除。命中以下任一，**才**允许重启对应性能方向的诊断：

1. 出现**新 workload**（bench 或真实程序）使 OPT-ENOUGH 指标退化到够用线外（几何平均
   >1.05x 或总耗时 >1.10x）；
2. 语言层新增可并行语义 / 显式向量提示，使此前负 ROI 的方向（SIMD/展开）出现正收益；
3. P0/P1/P2/P3 全部收口后，仍有明确预算且用户主动要求进一步压榨性能。

不满足以上而「只是想再快一点」——**一律不重启**，资源留给代替能力。

## 6. 一句话结论

> **性能已经够用（几何平均 0.57x、总耗时 0.91x，远超 ±5% 噪声阈值），性能优化正式冻结。
> 接下来的主线不再是「比 LLVM 更快」，而是「在功能、平台、正确性上让 LLVM 变得不必要」——
> 先清 P0 map key 泄漏（正确性底线），再补 P1 AArch64 实机语义，然后裁决 P2 语言特性，
> 最后 P3 文档收口。性能只作回归护栏，不再投入。**
